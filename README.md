# VR Minecraft — 게임 기획서

손으로 블록을 부수고 쌓아 무너진 구조물을 되살리는 VR 복셀 게임.

---

## 1. 게임 개요

| 항목 | 내용 |
|---|---|
| 게임 제목 | **VR Minecraft** (가제) |
| 장르 | VR / Voxel / Building Puzzle |
| 개발 엔진 | Unreal Engine 5.6.1 (C++) |
| 플랫폼 | PC VR (OpenXR / SteamVR), Virtual Desktop 스트리밍 |
| 시연 기기 | 삼성 갤럭시 XR + 컨트롤러 |
| 플레이 방식 | Single Player |
| 시점 | First Person (HMD) |
| 예상 플레이 시간 | 15분 (3단계 클리어 기준) |

### 한 줄 소개

> 복셀 세계를 직접 걸어다니며 필요한 블록을 손으로 캐내고, 허공에 떠 있는 청사진을 따라 구조물을 복원하는 VR 게임

## 2. 게임 컨셉

플레이어는 헤드셋을 쓰는 순간 절차적으로 생성된 복셀 지형 한가운데에 선다. 눈앞에는 **반투명한 청사진**이 떠 있다. 한때 거기 있었던 구조물의 윤곽이다.

화면 속 캐릭터를 조작하는 것이 아니라, **자기 손으로** 블록을 들고 있다. 오른손에 쥔 블록이 곧 조준기이자 도구다. 블록으로 지형을 겨누면 대상 블록에 윤곽선이 뜨고, 트리거를 누르고 있으면 균열이 번지다가 부서진다. 부순 블록은 손으로 들어온다. 그립을 쥐면 그 블록이 청사진의 빈 자리에 놓인다.

기존 마인크래프트가 마우스 커서로 하던 일을 **팔의 각도와 손의 위치로** 바꾸는 것이 이 프로젝트의 핵심이다.

### 핵심 키워드

- **Read** : 청사진을 읽고 어떤 블록이 몇 개 필요한지 파악한다
- **Mine** : 지형을 부숴 필요한 블록을 모은다
- **Build** : 청사진의 빈 자리에 정확한 블록을 채운다
- **Restore** : 구조물이 100% 복원되면 실체화되고 다음 단계가 열린다

### 차별점

| 요소 | 일반 복셀 게임 | 본 프로젝트 |
|---|---|---|
| 조준 | 화면 중앙 고정 크로스헤어 | 손에 든 블록의 앞면에서 나가는 레이 |
| 블록 선택 | 화면 하단 UI | 손목 안쪽에 붙은 핫바 위젯 |
| 목표 | 없음 (순수 샌드박스) | 청사진 복원 — 명확한 클리어 판정 |
| 피드백 | 시각 + 사운드 | 시각 + 사운드 + **컨트롤러 햅틱** |
| 몰입 | 모니터 | 1인칭 실제 스케일 (블록 1개 = 1m) |

## 3. 게임 목표 — 「복원」

### 규칙 세 가지

1. **부순 블록은 손으로 들어온다.** 핫바 슬롯은 블록 종류와 **보유 개수**를 함께 들고 있다. 설치하면 1 감소하고, 0이 되면 그 블록은 놓을 수 없다.
2. **청사진이 목표를 알려준다.** 각 단계의 시작 지점에 반투명 고스트 블록으로 이루어진 구조물이 떠 있다. 어느 자리에 어떤 블록이 필요한지 색으로 구분된다.
3. **청사진을 100% 채우면 클리어.** 모든 자리에 지정된 종류의 블록이 놓이면 구조물이 실체화되고 다음 단계가 열린다.

### 왜 이 목표인가

**자원 제약이 없으면 목표가 성립하지 않는다.** 블록이 무한이면 건축은 공짜다. 공짜인 일에는 목표를 붙일 수 없고, 플레이어가 지형을 파헤칠 이유도 사라진다. "부순 것만 놓을 수 있다"는 규칙 하나가 탐색·채굴·건축을 하나의 흐름으로 묶는다.

**개발 비용이 거의 들지 않는다.** 청사진 렌더링은 설치 미리보기용 **고스트 블록 시스템을 그대로 재사용**한다. 핫바·파괴·설치는 어차피 만든다. 새로 필요한 건 "청사진과 현재 월드를 비교해 진행도를 내는" 로직 하나뿐이고, 이건 순수 데이터 비교라서 **VR 없이 자동화 테스트로 검증**된다.

### 3단계 진행

| 단계 | 목표 구조물 | 필요 블록 | 새로 배우는 것 | 예상 |
|---|---|---|---|---|
| **1. 오두막** | 3×3×3 | 판자 12 | 파괴·설치·핫바 기본기 | 3분 |
| **2. 다리** | 협곡 횡단 1×8 | 돌 30 | 지하로 내려가 채굴, 아래를 보며 설치 | 5분 |
| **3. 탑** | 높이 10 | 혼합 60 | 비계를 쌓아 올라가며 건축 | 7분 |

단계가 올라갈수록 **필요한 블록이 손 닿는 곳에서 멀어진다.** 1단계는 눈앞의 나무를 부수면 끝이고, 2단계는 땅을 파야 하고, 3단계는 자기가 쌓은 블록을 밟고 올라가야 한다. 이동·조준·건축 난이도가 자연스럽게 올라간다.

### 실패 조건은 두지 않는다

제한 시간도, 체력도, 적도 없다. VR에서 실패 압박은 그대로 스트레스와 멀미로 돌아온다. 대신 클리어 시 **경과 시간**을 보여주고, 잘못 놓은 블록은 다시 부숴서 회수할 수 있게 한다.

## 4. Core Gameplay Loop

```text
청사진 확인 — 어떤 블록이 몇 개 부족한가
  ↓
지형 탐색 (이동 / 스냅 턴)
  ↓
필요한 블록 조준 → 트리거 홀드 → 파괴
  ↓
부순 블록이 핫바에 쌓임 (개수 +1)
  ↓
청사진으로 복귀
  ↓
핫바에서 해당 블록 선택 → 그립 → 설치 (개수 -1)
  ↓
진행도 갱신 (12 / 12)
  ↓
┌─ 부족 → 다시 탐색
└─ 100% → 구조물 실체화, 다음 단계
```

플레이어는 **부족한 것을 확인 → 캐러 간다 → 채운다**를 반복한다. 샌드박스의 자유도를 유지하면서도 매 순간 다음에 할 일이 분명하다.

## 5. 플레이어 조작

컨트롤러 물리 배치는 Quest Touch 기준 (왼손 X/Y, 오른손 A/B).

| 입력 | 기능 | 비고 |
|---|---|---|
| 오른쪽 스틱 | 스무스 이동 (HMD 기준 전후좌우) | 데드존 0.2 |
| 왼쪽 스틱 좌/우 | 핫바 이전 / 다음 슬롯 | 래치 처리 (한 번 밀면 한 칸) |
| 오른손 트리거 (홀드) | 블록 파괴 | 누른 시간이 블록 경도에 도달하면 파괴 |
| 오른손 그립 | 블록 설치 | 반쯤 누르면 고스트, 끝까지 누르면 설치 |
| 왼손 X / Y | 스냅 턴 좌 / 우 | 기본 45°, 30/45/90 옵션 |
| 오른손 A | 점프 | |
| 오른손 B | 메뉴 (예약) | MVP 미구현 |
| 왼손 트리거 / 그립 | 미사용 | 양손 대칭은 설정 플래그로 확장 가능 |

**스냅 턴을 스틱이 아니라 버튼에 둔 이유** — 오른쪽 스틱은 이동 전용이다. 왼쪽 스틱에 턴을 넣으면 핫바를 넘기다 실수로 시점이 돌아가 멀미가 난다.

## 6. 플레이어 기능

### 6.1 이동 (Locomotion)

- HMD가 바라보는 방향 기준 스무스 이동
- 스냅 턴 (스무스 턴 미제공 — 멀미 방지)
- 점프 / 중력 낙하
- 룸스케일 물리 이동 — 실제로 걸으면 캡슐이 HMD 위치를 따라감
- 이동 중 비네트 (옵션, 기본 켬)

### 6.2 조준 (Aiming)

- 레이 원점은 컨트롤러가 아니라 **손에 든 블록의 앞면 중심**, 방향은 컨트롤러 전방
- 사거리 4.5m
- 물리 트레이스가 아닌 **복셀 데이터 위 DDA 연산** — 충돌 메시가 없는 먼 청크도 조준되고 맞은 면의 법선이 정확하다
- 대상 블록에 와이어프레임 하이라이트

### 6.3 파괴 (Break)

- 트리거를 누르는 동안 진행도 누적, 블록 경도에 도달하면 파괴
- 진행도는 하이라이트 큐브에 **균열 단계**로 표시
- 조준 대상이 바뀌면 진행도 리셋
- 파괴 중 컨트롤러 햅틱 진동, 완료 시 파티클 + 사운드
- **부순 블록은 핫바에 들어온다** (돌 → 조약돌처럼 다른 블록으로 바뀌는 경우는 `UBlockDefinition`에 드롭 지정)

### 6.4 설치 (Place)

- 그립 절반 → 설치될 자리에 **반투명 고스트 블록** 미리보기
- 그립 끝까지 → 현재 핫바 슬롯의 블록 설치, 보유 개수 1 감소
- 보유 개수가 0이면 고스트가 흐려지고 설치 차단
- 설치 위치가 플레이어 캡슐과 겹치면 고스트가 빨갛게 변하며 설치 차단 (발밑에 놓고 끼이는 사고 방지)

### 6.5 핫바 (Hotbar)

- 슬롯 9칸, 각 칸이 **블록 종류 + 보유 개수**를 들고 있다
- 왼쪽 스틱 좌우로 슬롯 이동, **래치 처리**로 밀고 있어도 한 칸만 넘어감
- 현재 슬롯 표시는 두 곳
  - 오른손에 들린 블록 (실제 블록의 0.25배 크기 — 1m 큐브를 들면 시야를 가린다)
  - 왼쪽 손목 안쪽 핫바 위젯 (시계를 보듯 손을 돌리면 확인)
- 슬롯이 바뀌어도 메시 교체 없이 아틀라스 UV 오프셋만 갱신 → 월드 블록과 그림이 정확히 일치
- 빈 슬롯이거나 개수가 0이면 손 위 블록을 숨김

### 6.6 목표와 청사진 (Objective)

- 각 단계의 청사진은 데이터 에셋(`UStructureTemplate`)이 **상대 좌표 → 블록 id** 배열로 들고 있다
- 청사진은 고스트 블록을 **Instanced Static Mesh**로 한 번에 그린다 (60개를 개별 액터로 두면 드로우콜이 아깝다)
- 블록이 놓이거나 부서질 때마다 해당 좌표만 다시 비교해 진행도를 갱신한다 (전체 스캔 아님)
- 진행도는 손목 위젯에 `12 / 12` 와 프로그레스 바로 표시
- 100% 도달 시 고스트가 사라지고 실제 블록으로 확정, 완료 사운드 + 경과 시간 표시

### 6.7 월드 (World)

- 절차적 지형 생성 (2D 높이맵 노이즈 + 3D 동굴 노이즈)
- 플레이어 주변 렌더 거리만큼 청크 자동 로드 / 언로드
- 블록 1개 = 100 UU (1m), 청크 16×16×128
- 시연용 맵은 **시드 고정** — 협곡과 나무가 청사진 근처에 항상 같은 위치로 생성돼야 3단계 난이도 곡선이 유지된다
- 면 컬링 메싱, 청크 메시 생성은 워커 스레드 — VR에서 히치 한 번이 곧 멀미다

## 7. 에셋 계획

상세 표와 라이선스는 [docs/assets.md](docs/assets.md). 요약하면 다음 네 가지 원칙으로 움직인다.

### 7.1 마인크래프트 원본 리소스는 쓰지 않는다

텍스처·사운드 모두 Mojang 저작물이다. 리소스팩도 대부분 CC-BY-SA로 배포 조건이 붙는다. **직접 제작하거나 CC0만** 쓴다.

### 7.2 2단계 에셋 전략

`.uasset`은 Windows에서만 만든다(plan.md 1절). 그래서 맥에서 진행하는 복셀 코어 개발이 에셋을 기다리지 않도록 두 단계로 나눈다.

| 단계 | 시기 | 블록 외형 | 만드는 곳 |
|---|---|---|---|
| 프로토타입 | M0~M1 | 블록별 **버텍스 컬러 단색** | 맥, C++ 색상 테이블 |
| 최종 | M2~M3 | 텍스처 아틀라스 | Windows, 아틀라스 uasset |

프로토타입에서는 에셋 파일이 **0개**라 맥에서 복셀 코어 전체를 검증할 수 있다. 아틀라스가 들어올 때 메셔의 UV 출력만 켜면 되고 면 컬링·DDA·청크 로직은 손대지 않는다.

### 7.3 에셋 목록

| 종류 | 내용 | 확보 방법 |
|---|---|---|
| 블록 텍스처 | 512×512 아틀라스, 32px 타일 12종 (풀·흙·돌·조약돌·모래·통나무·판자·잎·유리·자갈) | **직접 제작** (Aseprite / Pixelorama, 2~3시간) |
| 손 메시 | 좌우 손 + 손가락 애니메이션 | **UE5 VR 템플릿의 MannequinsXR** (엔진 내장) |
| 사운드 | 파괴 3종·설치·채굴 루프·발소리 2종·UI 클릭·완료·앰비언트 | Kenney Audio / Freesound **CC0**, 일부 직접 녹음 |
| 파티클 | 파괴 파편, 설치 먼지 | Niagara 직접 제작, **외부 에셋 0** |
| 머티리얼 | 마스터 1개 + 인스턴스 4개 (월드·손·고스트·하이라이트) | 직접 제작 |
| 균열 표현 | 파괴 진행도 표시 | **절차적 노이즈** — 텍스처 불필요 |
| UI | 핫바 위젯, 진행도 바 | UMG + 아틀라스 타일, 폰트는 내장 Roboto |
| 스카이 | 그라디언트 스카이스피어 | 머티리얼 1개 |

파편 파티클은 **월드와 같은 아틀라스**를 써서 부순 블록과 색이 정확히 일치한다. 균열은 노이즈 임계값으로 그려 10단계 텍스처를 만들 필요가 없다.

### 7.4 배제 목록과 용량 예산

**안 쓰는 것:** Fab/마켓플레이스 대형 팩, Quixel Megascans, Nanite 메시, Lumen 의존 라이팅, 모션 블러. Forward Shading + MSAA 4x + 90fps와 정면으로 충돌한다.

**예산:** Content/ 총 **50MB 이하**, 현재 계획 합계 약 **23MB** (손 메시 15MB가 대부분). LFS가 커지면 머신 전환마다 pull이 느려진다.

## 8. 개발 범위

### MVP 포함

## 9. 개발 마일스톤

| 단계 | 내용 | 에셋 작업 | 확인 방법 |
|---|---|---|---|
| M0 | 프로젝트 뼈대, 클래스 스텁, LFS 설정 | 없음 | 맥/Windows 양쪽 컴파일 통과 |
| M1 | 복셀 코어 (청크·메셔·DDA·노이즈) | 버텍스 컬러 색상 테이블 | 데스크탑 디버그 폰으로 파괴/설치, 90fps |
| M2 | VR 폰과 이동 | MannequinsXR 임포트, palm 소켓 | VR Preview에서 걷기·턴·점프 |
| M3 | VR 상호작용 (조준·파괴·설치) | 아틀라스 12타일, 머티리얼, 절차적 균열 | 5m 안 블록을 정확히 지목해 부수고 놓기 |
| M4 | 개수 핫바 + 손에 든 블록 + 청사진 목표 | 핫바 위젯 UMG | 3단계 전부 클리어 가능, 블록 0개면 설치 차단 |
| M5 | 폴리싱, 성능 프로파일링, 시연 준비 | 사운드 10종, Niagara 2종, 스카이 | 실기기 15분 연속 플레이 무크래시 |
| M6 (스트레치) | Android XR 네이티브 패키징 | 저사양 아틀라스 256px | APK 단독 구동 |

목표 프레임 **90fps**, 최소 72fps. Forward Shading + MSAA 4x, Lumen/Nanite 미사용, 머티리얼 1개 + 텍스처 아틀라스 1개.

## 10. 기술 구조 요약

```text
AVRPawn
 ├─ VROrigin
 │   ├─ Camera (HMD)
 │   ├─ MotionController (Left)  ─ HandMesh + HotbarWidget
 │   └─ MotionController (Right) ─ HandMesh + HeldBlockMesh
 └─ Capsule (HMD 위치 추종, 이동/충돌)
```

| 폴더 | 역할 |
|---|---|
| `Voxel/` | 청크 데이터, 메시 생성, DDA 레이캐스트, 월드 생성 |
| `Player/` | VR 폰, 이동 컴포넌트, 데스크탑 디버그 폰 |
| `Interaction/` | 핫바, 블록 상호작용, 손에 든 블록, 청사진 목표 |
| `UI/` | 손목 핫바 위젯, 진행도 표시 |

핫바 데이터는 `UHotbarComponent` 한 곳에만 존재하고, 손 위 블록과 손목 위젯이 델리게이트를 구독해 따라간다. 청사진 판정은 `UObjectiveComponent`가 월드의 블록 변경 이벤트를 받아 처리한다.

상세 설계는 [docs/design.md](docs/design.md), 에셋은 [docs/assets.md](docs/assets.md), 일정과 리스크는 [docs/plan.md](docs/plan.md) 참고.
